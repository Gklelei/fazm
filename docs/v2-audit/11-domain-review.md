# 11 — Football Academy Domain Review

## What the schema actually models today

**Athlete** (`Athlete.prisma`): a flat record with a business key (`athleteId`) separate from the primary key (`id`). `dateOfBirth` is stored as **`String`**, not `DateTime`; `age` is a **separately-stored `Int?`**, not derived from DOB — meaning it can drift and needs a cron job (`update-age`) to stay correct rather than being computed on read. `height`, `weight`, `foot`, `hand` are all free-text `String` fields, not numeric/enum types. `positions String[]` is free text with no `Position` enum. An athlete belongs to exactly **one** `Batches` at a time via `batchesId` — there is no history of batch changes and no multi-team/squad concept. `AthleteAddress` and `AthleteMedicalAndEmergency` are 1:1 sub-tables (the medical one is a **static snapshot** — blood group, free-text `allergies`/`medicalConditions` arrays — not a dated log of medical events).

**Guardians**: `AthleteGuardian` and `AthleteEmergencyContact` are both **1-to-many from Athlete**, with no shared `Guardian` entity. This means **siblings sharing the same parent get that parent's name/email/phone duplicated on each athlete's own guardian row** rather than referencing one shared person record — and there is no guardian login/portal account, no guardian-initiated payment flow.

**Training** (`Training.prisma`): `Batches` = a cohort/group with optional `startDate`/`endDate` and `BatchSchedule[]` for recurring day/time slots. `training` (note the lowercase model name, inconsistent with `Athlete`/`Batches`) is one scheduled session, tied to one batch, one coach (`staff`), one `TrainingLocations`, with a `drills[]` relation and a separate `drillOrder String[]` for ordering (a manual-sync footgun — inline "DO NOT TOUCH" comments in the schema suggest this has already caused problems). `attendance` is **well-modeled**: properly linked per training session (`@@unique([trainingId, athleteId])`) with a real `AttendanceStatus` enum and an optional reason lookup — this is not a generic day-based blob, it's session-linked as it should be.

**Assessments** (`Assesment.prisma`): the **standout well-designed part of the schema**. Not a single numeric rating — a proper template system: `AssessmentTemplateSection` → `AssessmentMetric` (labeled skills within a section) → `Assessment` (one per athlete per training session, `@@unique([athleteId, trainingId])`) → `AssessmentResponse` (a per-metric grade using a 5-point ordinal `GradeRating` enum). This is trend-friendly — you can chart grade movement per athlete per metric over time — but the ordinal enum is hard-coded (adding a 6th grade level needs a migration and a full re-grading decision for existing history), and templates are global/singleton with no versioning: editing a section's metrics silently shifts the meaning of every historical assessment that scored against it, since responses only FK to a metric by ID with no snapshot of the label/order at scoring time.

**Finance** (`Finance.prisma`): billing is clearly modeled **per-athlete, not per-family** — `Invoice`, `AthleteSubscription`, and `Finance` (payments) all point directly at one athlete. A family with three children enrolled gets three fully independent subscriptions/invoices with no shared household balance or consolidated guardian-facing statement. Both recurring billing (`SubscriptionPlan` + `AthleteSubscription`, with a `SUB_FREQUENCY` enum and trial/auto-renew support) and one-off billing (`INVOICE_TYPE` enum: manual, late fee, item purchase) are supported — genuinely more sophisticated modeling than the rest of the schema. `Coupon` supports percentage/fixed discounts, once/repeating application, and usage limits, applicable to both subscriptions and invoices.

**Staff/roles** (`staff.prisma`): a flat, global `ROLES` enum (`COACH`, `ADMIN`, `DOCTOR`, `FINANCE`, `SUPER_ADMIN`) — there is no way to scope a coach's access to only their own batch/training sessions. Any `COACH` can, at the schema level, read or write any batch's data; whether the application layer restricts this further is covered in `02-security-audit.md`, and the audit found it largely does **not**.

**Settings** (`src/Modules/Settings`): this is cohort/group and reference-data management (batches, training locations, drills library) plus a genuine audit-log system (`AuditLog.prisma`), not a generic settings catch-all.

## Multi-tenancy

`academy` (`Utils.prisma`) is a **single global settings row** with no `id` referenced as a foreign key by any other model — confirming this is a **single-tenant** system (one academy per database/deployment). `AuditLog.academyId` exists as a column but has **no `@relation` at all** — it's a dangling, unenforced field, likely a leftover from an earlier multi-tenant idea that was abandoned. This matters for two reasons: (1) the authorization audit's IDOR risk is entirely about role/ownership scoping within one academy, not cross-tenant leakage, since there is no tenant boundary today; (2) if V2 ever wants to become a multi-academy SaaS product, essentially every model with a direct `athleteId`/`staffId` FK would need an `academyId` column added and backfilled — a large migration, not an incremental one, so this decision should be made deliberately and early if it's ever on the roadmap.

## Gaps that actually matter for this specific app (not a generic feature wishlist)

These are prioritized by how directly they connect to something the app already claims to do, per the audit's rule against recommending features the app has no current use for:

1. **No shared `Guardian` entity (highest-priority domain gap).** Given the module is literally named for guardians and billing is per-athlete, the inability to represent "one parent, several enrolled children" without duplicating that parent's contact details on every child's row is the single most consequential gap — it affects data quality (drift between duplicated copies), UX (no consolidated family view or statement), and any future guardian-portal/guardian-payment feature.
2. **No season/term concept**, despite `Finance.billingCycle` already being a free-text string (e.g. `"2024-12"`) standing in for one. As recurring billing logic grows, this stringly-typed period key will not sort, query, or report on cleanly — a real `Season`/`BillingPeriod` entity is a natural, low-risk addition given the billing model already implies the concept.
3. **`dateOfBirth` as a string and `age` as a separately-stored, driftable field**, with no age-group concept (e.g. U10/U12) despite the app already tracking foot/hand dominance — for a youth academy, age-group is arguably more operationally relevant than foot dominance and would naturally derive from a properly-typed DOB.
4. **Flat, unscoped staff roles.** Given multiple coaches likely each own specific batches, a `COACH` role with no batch-scoping is both a security exposure (already flagged) and a missing product feature (a coach currently has no natural "my batches" view enforced anywhere below the UI layer).

## Gaps that were considered and are **not** recommended for V2 given current scope

- **Fixture/match tracking, scouting, player promotion pipelines, disciplinary records** — the `training` model only represents practice sessions, and assessments/attendance both hang off training sessions specifically. Nothing in the current app claims to manage match days, so building match/fixture infrastructure now would be exactly the kind of speculative, unrequested feature the audit was asked to avoid recommending.
- **Deep injury/medical event logging** (dated history vs. static snapshot) — the current `AthleteMedicalAndEmergency` is shallow, but this is reasonable given the app's current scope is front-office/training operations, not sports medicine; a static "known conditions/allergies" snapshot is adequate for that scope and upgrading it should wait until there's a concrete driver (e.g. a medical-staff-facing feature request).

## Summary for V2 domain planning

The domain model's core weaknesses are consistent with the rest of this audit's overall theme: parts of it (assessments, subscription billing) are genuinely well-designed, while other parts (guardian/family modeling, DOB/age typing, role scoping) are undermodeled relative to what the product already tries to do. None of the gaps above require a schema rewrite — they are additive changes (a `Guardian` entity with a join table, a `Season`/`BillingPeriod` entity, converting `dateOfBirth` to `DateTime`, adding batch-scoped role assignments) that can be sequenced into the phased roadmap in `13-v2-roadmap.md` without disrupting the parts of the schema that already work well.
